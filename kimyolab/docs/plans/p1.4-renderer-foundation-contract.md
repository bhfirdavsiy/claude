## 2. Renderer boundary (target)

```
Chemistry Model (domain)          — kimyoviy haqiqat: reaksiya, mahsulot, holat hosilasi
      ↓  (engine/adapter)
RendererModel                     — faqat ko‘rsatish uchun, versiyalangan, serializable holat
      ↓
Renderer (DOM | accessible text | kelajakda canvas/WebGL)
      ↓  foydalanuvchi harakati
Intent                            — {kind, capability, payload} — kimyo hisoblamaydi
      ↓  ReferencePracticeSession → adapter → domain
Domain Model                      — natija → yangi RendererModel
```

**Renderer quyidagilarni hisoblamaydi va bilmaydi:**
- chemistry truth (reaksiya, mahsulot, to‘g‘ri javob);
- mastery (`MASTERY_COMPUTED_IN_PRESENTATION` guard);
- progress va persistence (`LAYER_IMPORTS_PERSISTENCE`, `STATE_MUTATION_OUTSIDE_BOUNDARY`);
- readiness va approval (`READINESS_DERIVED_IN_PRESENTATION`, P1.3).

Renderer faqat `RendererModel`ni chizadi va `Intent` chiqaradi.

## 3. Renderer capability contract (minimal taklif)

Mavjud `ActivityExecutionPlan {activityId, engine, runtime, capability, configSource, configVersion}` saqlanadi. Renderer uni kengaytiradi, parallel taksonomiya yaratmaydi:

```ts
interface RendererCapability {
  id: string;                     // plan.capability bilan bir xil nom maydoni, masalan 'reference.atom-builder'
  version: string;                // semver: RendererModel sxemasi versiyasi
  rendererModelSchema: string;    // masalan 'kimyolab.renderer.atom-state.v1'
  intents: string[];              // chiqaradigan Intent turlari: ['simulation-action']
  accessibility: {                // majburiy (§6) — yo‘q bo‘lsa ro‘yxatdan o‘tmaydi
    keyboard: true; nonColorCues: true; screenReaderSummary: true;
    reducedMotion: 'static'|'reduced'; nonVisualAlternative: 'text-state'|'table'|'steps';
  };
}
```

- **`inputSchema` o‘rniga `rendererModelSchema`.** Renderer config’ni o‘qimaydi, faqat engine’dan kelgan `RendererModel`ni o‘qiydi.
- **`outputEvents` → `intents`.** Ular mavjud `PracticeCommand` turlari (`session.ts:22-26`), yangi event bus emas.

## 4. RendererRegistry vazifasi (kelajak)

```
resolve(plan.capability, rendererModelSchema version) → RendererImplementation | RENDERER_UNAVAILABLE
```

- **Kalit:** `capability id + version`. **`activityId` hech qachon kalit emas.** Guard `RENDERER_SELECTED_BY_ACTIVITY_ID` (P1.3) presentation’da `switch(page.id){case 'practice.…'}` yoki `id==='practice.…'`ni hozirdan rad etadi.
- **Fail-closed:** mos renderer yo‘q bo‘lsa, launch qilinmaydi va lokalizatsiya qilingan matn ko‘rsatiladi. Bu readiness bilan bir xil semantika (`BLOCKED`), default renderer’ga jim tushish yo‘q (`EXECUTION_RUNTIME_UNKNOWN` bilan bir xil tamoyil).
- **Bir capability — bir nechta renderer (DOM, text):** tanlov foydalanuvchi sozlamasiga qarab bo‘ladi (reduced motion, screen reader), activity’ga qarab emas.

## 5. Capability versioning

Content pack’dagi execution plan talab yozadi, masalan:

```
rendererRequirement: { capability: 'beta2-advanced.electrolysis-experiment', range: '>=1 <2' }
```

- Build’da (`content:pack`) talabni qondiradigan renderer bo‘lmasa → readiness `BLOCKED` (`RENDERER_UNAVAILABLE`).
- Runtime’da registry versiyani qayta tekshiradi. Mos kelmasa, launch fail-closed.
- `RendererModel` sxemasi o‘zgarsa major versiya oshadi. Eski content pack eski major talab qiladi, shuning uchun ikkala major yonma-yon yashashi mumkin.
- **Mavjud precedent:** `engineCompatibility.range` (`^1.0.0`) activity va engine uchun. `pilot:status` uni `technical.version-compatibility`da tekshiradi.

Hozir implementatsiya qilinmaydi.

## 6. Model va renderer ajralishi

Bir xil `RendererModel` (masalan `AtomState {protons, neutrons, electrons, element, massNumber, charge, isotope}`) turli renderer’lar bilan ishlaydi:
- **DOM renderer:** tugmalar va holat qatori (hozirgi);
- **accessible text renderer:** “Uglerod-14, neytral atom, 6 proton, 8 neytron, 6 elektron”;
- **kelajakdagi canvas/WebGL:** zarrachalar.

Hammasi **bir xil** domain hosilasini chizadi. Element, izotop va zaryad reducer’da hisoblanadi. Renderer ichida kimyoviy hisob yo‘q. Renderer faqat model bergan qiymatni ko‘rsatadi.

## 7. Accessibility contract (dizayn qismi, keyinga surilmaydi)

Har renderer ro‘yxatdan o‘tishi uchun quyidagilar **majburiy**:

| Talab | Mazmuni | Tekshiruv (P1.4) |
|---|---|---|
| keyboard | Har intent klaviatura bilan beriladi, fokus tartibi mantiqiy | E2E: faqat klaviatura bilan yechish (P1.3 atom E2E buni qiladi) |
| non-color cues | Holat rang bilan birga matn yoki shakl bilan ham beriladi (cho‘kma rangi + “cho‘kma”) | DOM: har rang o‘zgarishining matn ekvivalenti |
| screen-reader summary | `aria-live` holat xulosasi, raw kod yo‘q | E2E: `RAW_CODE` regex, `role=status` |
| reduced motion | `prefers-reduced-motion`da animatsiya yo‘q yoki statik | CSS/E2E |
| non-visual alternative | text-state / jadval / qadamlar ro‘yxati | renderer capability’da e’lon qilinadi |

Talabdan birortasi e’lon qilinmagan capability registry’ga **kirmaydi**.

## 9. Black-swan testi

**Savol:** bu model-based interaction bo‘ladimi yoki formani chiroyli animatsiya qilamizmi?

- **atom-builder: PASS.** Renderer faqat reducer hosilasini chizadi.
- **ionic-precipitation: RISK → PASS sharti bilan.** Reaktiv tanlash intent’i bo‘lsa va faqat matcher qaytargan kuzatuv ko‘rsatilsa PASS. Modellashtirilmagan juftlik rad etiladi, kimyo o‘ylab topilmaydi.
- **hydrolysis-medium: domain’da PASS, hozirgi UI’da FAIL.**
- **electrolysis: FAIL.** 1 yozuvli model bilan “simulation” deb atalmaydi.
- **single-field: FAIL.**

Hozirgi tajriba sahnasi (`render.ts:69-71`, label regex → CSS klass) **canned animation**. P1.4 da u RendererModel’ga bog‘lanmaguncha “simulation” deb atalmaydi.
